# รอบ 2W — แผนที่โลก · มอน EX · ดวลกับผู้เล่นคนอื่น

> สัญญาที่ทุกทีมยึดในรอบนี้ | PM เป็นเจ้าของ | 20 ก.ย. 2026
> **รอบนี้ยังไม่ต้องใช้ภาพแผนที่** — ภาพกำลังรอจากเจ้าของโปรเจกต์ (ดู `docs/worldmap-art-prompt.md`)
> ทุกอย่างในเอกสารนี้ทำและทดสอบได้โดยไม่มีภาพ

---

## 1. ทำไมต้องมีรอบนี้

เจ้าของโปรเจกต์อยากได้แผนที่โลกแทนหอคอยอย่างเดียว แต่ละที่กดเข้าไปเจอ 10 เวฟ สุ่มมอน
มีโอกาสเจอ EX และถ้าอีกคนกดเข้าโซนเดียวกันพร้อมกันก็ได้สู้กัน

**เหตุผลที่ PM เห็นด้วย ไม่ใช่เพราะมันสวย:** ตอนนี้หลักสูตรที่ซ่อนในเกมปลดล็อก *ไวยากรณ์*
ตามชั้น (ชั้น 1 ได้ `if`, ชั้น 6 ได้ `and`) แต่แผนที่เปิดให้ทำสิ่งที่ดีกว่า — **แต่ละภูมิภาค
บังคับ "กลยุทธ์" คนละแบบ** ซึ่งเป็นสิ่งที่เราอยากสอนจริง ๆ

กำแพงที่เป็น *แนวคิด* แข็งแรงกว่ากำแพงที่เป็น *ตัวเลข*: คนที่ไม่เขียน `has_debuff()` จะไม่ผ่าน
ภูเขาไฟไม่ว่าเลเวลเท่าไร ต่างจากตอนนี้ที่รอบ 2P วัดได้ว่าคนไม่คิดยังไต่ถึงชั้น 4 ด้วยสเตตัสล้วน

## 2. กฎเหล็กของรอบนี้: อย่าทิ้งเลขชั้น

**`floor` ยังเป็นแกนความยากภายในเหมือนเดิม** ภูมิภาคเป็นชั้นที่วางทับ ไม่ใช่ของที่มาแทน

```
ภูมิภาค = ธีม + สระมอน + บทเรียน + ช่วงความยาก
ความยากจริงของการรบหนึ่งรอบ = floorBase + depth - 1   (ส่งเข้า runBattle เหมือนเดิม)
```

เหตุผล: รอบ 2P เพิ่งกวาดค่าจนเข้าเกณฑ์ B1–B5 ครบ (ดู `docs/design-round2p.md` §2 และ
`docs/measurements/tune-after-2p.txt`) ถ้าเปลี่ยนหน่วยความยากตอนนี้ งานวัดทั้งหมดเป็นโมฆะ
**และ `npm run tune -w engine` ต้องยังผ่านครบทุกข้อเมื่อจบรอบนี้** — ถือเป็นเกณฑ์รับงาน

ภูมิภาคทับซ้อนช่วงความยากกันได้และ*ควร*ทับ เพื่อให้ผู้เล่นที่ติดที่หนึ่งมีที่อื่นให้ไป
— ซึ่งแก้ปัญหาที่หอคอยมี: ตันชั้น 4 แล้วตันเลย ไม่มีทางอื่น

#### แก้กฎของตัวเอง (22 ก.ย. 2026) — "เลขชั้นเดียว" ถูกใช้เกินหน้าที่ของมัน

**ย่อหน้าข้างบนยังถูกทุกตัวอักษร แต่รอบ 2W เอาไปใช้ผิดที่หนึ่งแห่ง** และนั่นทำให้
เหตุผลทั้งหมดของรอบนี้เป็นโมฆะโดยที่ไม่มีใครเห็นจนกว่าจะมีคนเล่นจนจบ

ของจริงที่ลงไป: `regionProgress()` คิดความคืบหน้าของ *ทุก* ภูมิภาคจาก `highest_floor`
ก้อนเดียว — `cleared = min(depths, highestFloor - floorBase + 1)` PM เขียนกฎนี้เอง
โดยตั้งใจ เพื่อให้ "ชนะความยาก N ที่ไหนก็ได้ = เข้าความยาก N ที่ไหนก็ได้" ซึ่งเป็นวิธี
ทำให้ "ตันที่หนึ่งมีที่อื่นให้ไป" เป็นจริงโดยไม่ต้องมีตารางที่สอง

**สิ่งที่คิดไม่ครบ:** กฎเดียวกันนั้นแปลว่า **"ไม่ต้องไปที่ไหนเลยก็ได้ทุกที่"**
รอบ 2T วัดออกมาจากของจริง (`docs/measurements/playtest-2t.txt` ข้อ [2]): เคลียร์หอคอย
ชั้น 9 แล้ว หมู่เกาะ · ซากปรักหักพัง · ดินแดนน้ำแข็ง กลายเป็น `completed: true`
**ทั้งที่ไม่เคยยิง `enter` เข้าไปเลยสักครั้ง** ผู้เล่นทดสอบสองคนเจอตรงกัน
คนหนึ่งจบหกภูมิภาคโดยเล่นจริงภูมิภาคเดียว

ผลคือบทเรียนของทุกโซน (§3 `lessonTh` — เหตุผลข้อเดียวที่ §1 ยกมาเห็นด้วยกับแผนที่)
อยู่นอกเส้นทางหลัก **โดยโครงสร้าง** ไม่ใช่เพราะเขียนบทเรียนไม่ดี

**ความผิดพลาดที่แท้จริงคือการรวมคำถามสองข้อเป็นตัวเลขเดียว:**

| คำถาม | แหล่งความจริงที่ถูก |
|---|---|
| "โซนนี้ *เข้า* ได้หรือยัง" | `highest_floor` — เลขชั้นเดียวของเกม **ไม่เปลี่ยน** |
| "โซนนี้ *ผ่าน* ไปกี่รอบแล้ว" | ตารางต่อ (ผู้เล่น × ภูมิภาค) — ต้องเล่นจริงเท่านั้น |

ข้อกังวลเดิมที่ทำให้ไม่กล้าเก็บตารางแยก ("จะมีแหล่งความจริงสองแหล่งที่เพี้ยนจากกัน")
ไม่เกิด เพราะสองช่องนี้ตอบคนละคำถาม ไม่ใช่คำถามเดียวกันสองคำตอบ

แก้ที่รอบ 2F §3.2 — `region_progress(user_id, region_id, depth_cleared)`
การ *ปลดล็อก* ยังเป็นกฎของย่อหน้าข้างบนทุกตัวอักษร: ตันที่ภูเขาไฟยังเดินไปดินแดนน้ำแข็ง
ได้ทันทีโดยไม่เคยเล่นมัน เปลี่ยนแค่ว่าเข้าไปแล้วเริ่มที่รอบ 1 ไม่ใช่โผล่กลางโซน

**บทเรียนสำหรับรอบหน้า:** เวลาเขียนว่า "ใช้ตัวเลขที่มีอยู่แล้ว ไม่ต้องเพิ่มตาราง"
ให้ถามต่ออีกข้อเสมอว่า *ตัวเลขนั้นตอบคำถามกี่ข้อ* — ถ้ามากกว่าหนึ่ง มันจะตอบข้อที่สอง
ผิดในวันที่เกมโตพอ และความผิดนั้นจะอ่านไม่ออกจากโค้ด เพราะโค้ดมีบรรทัดเดียวและดูสมเหตุสมผล

## 3. โครงข้อมูลภูมิภาค

อยู่ใน `gamedata.json` ทั้งหมด เพิ่ม/แก้ภูมิภาคได้โดยไม่แตะโค้ด

| ช่อง | ความหมาย |
|---|---|
| `id` | คีย์ภายใน เช่น `volcano` |
| `nameTh` | ชื่อที่ผู้เล่นเห็น |
| `floorBase` · `depths` | ความยากรอบที่ N = `floorBase + N - 1` |
| `pool` | id ของ archetype ที่โผล่ในโซนนี้ (ถ้าเว้น = ใช้สระรวมตามเดิม) |
| `threatRole` | บทบาทของ "ตัวอันตราย" ที่การันตีต่อเวฟ (ค่าเริ่มต้น `bruiser` ตามรอบ 2P) |
| `lessonTh` | บทเรียนของโซนนี้ เขียนให้ผู้เล่นอ่านบนการ์ด เช่น "มอนที่นี่ตีแรงแต่ช้า — ลองใช้ `defend()` สลับกับโจมตี" |
| `eliteChance` | โอกาสที่รอบนั้นจะมี EX (0..1) |
| `hotspot` | ตำแหน่งบนภาพแผนที่ `{ x, y, r }` เป็นสัดส่วน 0..1 ของความกว้าง/สูง |

**`hotspot` ใส่ค่าชั่วคราวไปก่อนได้** ตอนภาพมาถึงค่อยปรับตัวเลขให้ตรงกับภาพจริง —
นี่คือเหตุผลที่รอบนี้ไม่ต้องรอภาพ

**หอคอยยังอยู่** เป็นภูมิภาคหนึ่งที่มี `depths: 10` และ `floorBase: 1` = บันไดตรง ๆ เหมือนเดิม
ของเก่าทั้งหมดจึงยังเล่นได้ และเป็นทางถอยถ้าแผนที่มีปัญหา

## 4. มอน EX

**กติกาที่ห้ามผิด: ดวงต้องไม่เป็นตัวตัดสินว่าผ่านหรือไม่ผ่าน**

เกมนี้สัญญากับผู้เล่นว่า "โค้ดดีขึ้นแล้วผ่าน" ถ้าจู่ ๆ มี EX โผล่มาแล้วแพ้ทั้งที่โค้ดเหมือนเดิม
สัญญานั้นเป็นโมฆะทันที จึงต้อง:

1. **สุ่มตอนกดเข้า แล้วบอกก่อนเริ่ม** — ผู้เล่นต้องเห็นว่า "รอบนี้มี EX" ก่อนที่การรบจะเริ่ม
   ไม่ใช่โผล่มากลางทาง
2. **ไม่เกิน 1 ตัวต่อรอบ** และรู้ล่วงหน้าว่าจะอยู่เวฟไหน
3. **แพ้เพราะ EX ต้องไม่เสียความคืบหน้าที่มีอยู่** — ถือว่ารอบนั้นไม่ผ่าน จบ ไม่ลดชั้นที่เคยผ่าน
4. EX ต้องคุ้มที่จะสู้ — ดรอปดีกว่าปกติอย่างเห็นได้ชัด ไม่งั้นผู้เล่นจะเรียนรู้ที่จะกดออกแล้วเข้าใหม่

**ตัวเลขทั้งหมดอยู่ใน gamedata** — ตัวคูณสเตตัส ตัวคูณดรอป และ `eliteChance` ต่อภูมิภาค

## 5. ดวลกับผู้เล่นคนอื่น

### 5.1 ทำไมมันถูกกว่าที่คิด

เกมนี้เป็น auto-battle จากโปรแกรมที่เก็บไว้แล้ว **ตอนสู้ไม่มีใครต้องกดอะไรเลย**
เซิร์ฟเวอร์รู้โปรแกรมของทั้งสองฝ่าย คำนวณครั้งเดียว แล้วส่ง event log ชุดเดียวกันให้ทั้งคู่ดู

**ไม่ต้องซิงก์เรียลไทม์ · ไม่ต้อง input sync · ไม่ต้อง rollback · ไม่ต้องมีเซิร์ฟเวอร์จับคู่แยก**
สิ่งเดียวที่สร้างใหม่คือตารางบอกว่า "ตอนนี้ใครอยู่โซนไหน"

ยืนยันแล้วว่า engine รองรับอยู่แล้ว: `programOf()` ใน `battle.ts` เช็ก `programSource`
**ก่อน** เช็ก `side === 'enemy'` ตัวละครฝั่งศัตรูที่พกโปรแกรมมาจึงใช้โปรแกรมนั้นได้เลย

### 5.2 ปัญหาที่ต้องออกแบบเผื่อตั้งแต่แรก

**ตอนนี้เรามีผู้เล่นสองคน** โอกาสกดพร้อมกันเกือบเป็นศูนย์ ถ้าทำแค่ "เจอกันตอนออนไลน์พร้อมกัน"
ฟีเจอร์จะตายตั้งแต่วันแรก จึงทำเป็น**ระบบเดียว**:

```
หาคู่ดวล:
  1. มีผู้เล่นอื่นอยู่โซนเดียวกันตอนนี้ และเลเวลใกล้กัน  → ใช้คนนั้น
  2. ไม่มี → ใช้สแนปช็อตของผู้เล่นที่เพิ่งเล่นในช่วงเลเวลเดียวกัน
  3. ไม่มีอีก → รอบนั้นไม่มีเวฟดวล (ไม่ใช่เรื่องผิดปกติ)
```

ทั้งสองทางใช้โค้ดเส้นทางเดียวกันเป๊ะ ผู้เล่นแทบแยกไม่ออก และระบบใช้ได้ตั้งแต่มีคนเล่นสองคน
ไปจนถึงมีเป็นพัน — **ข้อ 2 คือสิ่งที่ทำให้ฟีเจอร์นี้มีชีวิตในวันที่เราเปิดตัว**

### 5.3 กติกา

- **จับคู่ตามช่วงเลเวล** — lv30 เจอ lv5 ไม่ใช่การต่อสู้ เป็นการรังแก กำหนดช่วงใน gamedata
- **การดวลเป็นแมตช์แยก เลือดเต็มทั้งคู่ ไม่กินเลือดของรอบนั้น**
- **ประกาศก่อน** เหมือน EX — ผู้เล่นต้องรู้ว่ารอบนี้จะเจอใคร ก่อนที่จะเริ่ม
- **สแนปช็อตต้องไม่ผูกกับบัญชีแบบเปิดเผยเกินจำเป็น** — ส่งแค่ชื่อผู้เล่น คลาส เลเวล และโปรแกรม

#### แก้สเปกของตัวเอง (21 ก.ย. 2026) — ข้อ 2 เดิมเขียนผิด

ข้อ 2 เดิมเขียนว่า *"แพ้แล้วเสียแค่เวฟนั้น ไม่ล้มทั้งรอบ — ผู้เล่นเดินต่อไปเวฟถัดไปได้
ด้วยเลือดที่เหลือ"* คือให้การดวลเป็นเวฟหนึ่งในสิบเวฟ สู้ด้วยเลือดที่เหลืออยู่ตอนนั้น

**มันขัดกับเหตุผลทั้งหมดของการมีเวฟดวล** ถ้าสู้ด้วยเลือดที่เหลือ ผู้ชนะถูกตัดสินด้วย
"เวฟ 1-5 ที่ผ่านมาสุ่มมอนมาโหดแค่ไหน" ไม่ใช่ด้วยโปรแกรม — เป็นความผิดพลาดแบบเดียวกับ
ที่เพิ่งแก้ไปสองที่ในรอบนี้ (ยั่วยุที่ไม่มีผลตอนสู้คนเดียว · โล่ที่คิดจาก matk)
คือปล่อยให้อย่างอื่นตัดสินแทนสิ่งที่เกมสัญญาว่าจะวัด

และวัดมาแล้วว่าความต่างมีจริง: ที่ `duelHpMult` 1.5 **คนที่เขียนโปรแกรมเป็นชนะคนที่
ตีอย่างเดียว 97-100%** เมื่อคลาสและสเตตัสเท่ากัน (ดู `docs/measurements/duel-after-2w.txt`)
ตัวเลขนั้นจะหายไปทันทีถ้าฝ่ายหนึ่งเข้าดวลด้วยเลือด 20%

**ของจริงที่ทำ:** การดวลเป็นแมตช์แยกด้วย `runDuel` เลือดเต็มทั้งคู่ ประกาศก่อนลงโซน
เล่นให้ดูหลังจบรอบ ไม่มีดรอป ไม่มี EXP และไม่แตะผลของรอบนั้นเลย
เจตนาเดิมของข้อ 2 — *"ของแถมที่น่าตื่นเต้น ไม่ใช่กำแพงที่ผู้เล่นควบคุมไม่ได้"* — ยังอยู่ครบ
และแรงกว่าเดิมด้วยซ้ำ เพราะตอนนี้การดวลไม่มีทางทำให้รอบที่กำลังไปได้ดีพังได้เลย

ต้นทุนที่ยอมจ่าย: ไม่ต้องแก้ `simulateWaves` แม้แต่บรรทัดเดียว — golden fixture ของรอบนี้
จึงยังคุ้มครองแกนการรบอยู่เหมือนเดิม ส่วนที่เสียไปคือความรู้สึก "โดนดักกลางทาง"
ซึ่งเป็นความรู้สึกที่ §4 สั่งห้ามอยู่แล้วในกรณีของ EX

### 5.4 ของแถมที่คุ้มที่สุดในรอบนี้

**แพ้แล้วให้ดูโค้ดของคนที่ชนะได้**

เรามีแผงแสดงโค้ดในฉากต่อสู้อยู่แล้ว (เฟส 2B-2) ต้นทุนแทบเป็นศูนย์ แต่มันคือช่องทางการเรียนรู้
ที่ดีที่สุดที่เกมนี้จะมีได้ — เห็นโปรแกรมที่เก่งกว่าตัวเอง พร้อมบรรทัดที่ทำงานจริงในการรบที่เพิ่งแพ้ไป
นี่คือสิ่งที่หนังสือสอนเขียนโปรแกรมทำไม่ได้

## 6. เกณฑ์รับงาน

| # | เกณฑ์ | วัดยังไง |
|---|---|---|
| W1 | `npm run tune -w engine` ยังผ่าน B1–B5 ครบ | ความยากเดิมต้องไม่เพี้ยนเพราะการเพิ่มภูมิภาค |
| W2 | ผู้เล่นสองคนที่เข้าโซนเดียวกัน **ได้ event log ชุดเดียวกันเป๊ะ** | เทียบ JSON ตรง ๆ ไม่ใช่ดูว่า "คล้ายกัน" |
| W3 | EX ถูกประกาศก่อนการรบเริ่มเสมอ และไม่เกิน 1 ตัวต่อรอบ | ยิง API จริงหลายรอบแล้วนับ |
| W4 | ไม่มีผู้เล่นอื่นออนไลน์ → ยังเจอเวฟดวลจากสแนปช็อตได้ | ทดสอบด้วยบัญชีเดียวออนไลน์ |
| W5 | ฝ่ายแพ้เปิดดูโค้ดฝ่ายชนะได้ | คลิกผ่าน UI จริง |

## 7. สิ่งที่ตั้งใจ *ไม่* ทำในรอบนี้

- **co-op ลงด่านด้วยกันจริง** — คนละเรื่องกับการดวล ต้องจูน balance ใหม่ทั้งชุด (มอนแรงขึ้น 50%/คน)
  และแก้ determinism ของหลายโปรแกรมพร้อมกัน ยังอยู่เฟส 3
- **แผนที่ที่วาดเอง** — รอภาพจากเจ้าของโปรเจกต์ รอบนี้ใส่ `hotspot` ชั่วคราวไว้ก่อน
- **ห้องซ้อม** — ยังค้างจาก 2B-3 และ **ยังเป็นสิ่งที่แก้ปัญหาวงจรช้าได้จริงกว่าแผนที่**
  PM บันทึกไว้ว่าแผนที่ทำให้ "เลือกที่จะไป" น่าสนใจขึ้น แต่ไม่ได้ทำให้รอบการลองผิดลองถูกสั้นลงเลย

## 8. สัญญา API (PM ล็อก 21 ก.ย. 2026 — ฝั่ง server และ client ยึดตามนี้)

### 8.1 ทำไมต้องแยกเป็น "กดเข้า" แล้วค่อย "สู้"

§4 ข้อ 1 กับ §5.3 บังคับว่า EX และคู่ดวลต้อง **ประกาศก่อนการรบเริ่ม** ถ้ายิงครั้งเดียวแล้ว
ได้ผลรบกลับมาพร้อมกัน คำว่า "ก่อน" ไม่มีความหมาย เพราะทุกอย่างถูกตัดสินไปแล้วตอนที่ผู้เล่นเห็น

จึงเป็นสองจังหวะ: `enter` (ประกาศ + จองที่ในทะเบียนโซน) → `fight` (ลงมือ)

**ไม่มีตาราง "รอบที่ค้างอยู่" เพิ่ม** — `zone_presence` เป็นตัวจำเอง:
`seed` ของรอบคำนวณจาก `(user_id, region_id, depth, entered_at)` ซึ่งอยู่ในแถวนั้นครบแล้ว
`fight` จึงคำนวณ seed เดิมออกมาได้เสมอ และ EX ที่ประกาศกับ EX ที่ลงสนาม
เป็นการสุ่มครั้งเดียวกันโดยโครงสร้าง ไม่ใช่โดยความบังเอิญ

ส่วนคู่ดวลเลือกจากฐานข้อมูล (ใครอยู่ในโซนตอนนี้) ซึ่งเปลี่ยนได้ระหว่างสองจังหวะ
จึง **เขียน id ของคู่ที่ประกาศลงแถวทะเบียนตอน `enter`** (`duel_user_id` / `duel_snapshot_id`)
คำประกาศกับคู่ที่เจอจริงจึงตรงกันเสมอแม้อีกฝ่ายจะกดออกไปแล้ว

### 8.2 `GET /api/world`

```jsonc
{
  "regions": [{
    "id": "greenwood", "nameTh": "ป่าเขียว",
    "floorBase": 1, "depths": 10, "floorRange": [1, 10],
    "lessonTh": "...", "eliteChance": 0.12,
    "hotspot": { "x": 0.372, "y": 0.492, "r": 0.062 },
    "depthCleared": 3, "maxDepthAllowed": 4, "completed": false, "unlocked": true,
    "playersHere": 1          // จากทะเบียนโซน กวาดของหมดอายุทิ้งก่อนนับ
  }],
  "mapImage": "/worldmap.jpg",
  "highestFloorCleared": 3
}
```

> **แก้ความหมายในรอบ 2F §3.2 (22 ก.ย. 2026) — รูปร่าง JSON ไม่เปลี่ยนสักช่อง**
> `depthCleared` มาจากตาราง `region_progress` ของโซนนั้นจริง ๆ (0 = ยังไม่เคยผ่านรอบไหน)
> และ `maxDepthAllowed` แปลว่า **"รอบถัดไปของโซนนี้"** ไม่ใช่ "รอบที่เทียบเท่ากับความยาก
> สูงสุดที่เคยชนะที่ไหนก็ได้" · `unlocked` กับ `highestFloorCleared` ยังเป็นกฎเดิมทุกตัวอักษร
> ดูเหตุผลที่ท้าย §2 · `completed` ของโซนที่ไม่มีการรบ (`depths: 0` เช่นเมือง) ตอบ `false`
> แล้ว จากเดิมที่ตอบ `true` เพราะ `0 >= 0`

### 8.3 `POST /api/world/:regionId/enter`  body `{ "depth": 4 }`

ตรวจ `depth <= maxDepthAllowed` ไม่งั้น 400 · เขียน/ทับแถวทะเบียนโซน · คืน **คำประกาศ**:

```jsonc
{
  "regionId": "greenwood", "depth": 4, "floor": 4,
  "nameTh": "ป่าเขียว", "lessonTh": "...",
  "elite": { "wave": 6, "archetypeId": "brute", "nameTh": "..." },   // null = รอบนี้ไม่มี
  "duel": {                                                          // null = รอบนี้ไม่มีคู่
    "username": "dew", "classId": "mage", "level": 7,
    "live": true                    // true = อยู่ในโซนตอนนี้จริง · false = สแนปช็อต
  },
  "expiresAt": 1789737185572
}
```

### 8.4 `POST /api/world/:regionId/fight`  (ไม่มี body — ใช้แถวทะเบียนที่ `enter` เขียนไว้)

ไม่มีแถวทะเบียน หรือ `region_id` ไม่ตรง หรือหมดอายุ → **409** `{ error: "ต้องกดเข้าโซนก่อน" }`

```jsonc
{
  "result": { /* BattleResult เหมือน /tower/challenge ทุกช่อง */ },
  "announce": { /* ก้อนเดียวกับที่ enter คืน — client เทียบได้ว่าตรงกัน */ },
  "duel": {                       // null = รอบนี้ไม่มีคู่ดวล
    "opponent": { "username": "dew", "classId": "mage", "level": 7, "live": true },
    "events": [ /* CombatEvent[] ของการดวล */ ],
    "won": true,                  // มุมมองของผู้เรียก
    "byTimeout": false, "rounds": 9,
    "opponentProgram": "..."      // §5.4 — ส่งเสมอ ไม่ใช่เฉพาะตอนแพ้
  },
  "character": { /* ... */ }, "leveledUp": false, "statsGained": { /* ... */ }
}
```

**เกณฑ์ W2 เป็นจริงด้วย `duel_matches` ไม่ใช่ด้วยความหวัง:** `match_key` ของคู่ที่ออนไลน์ทั้งคู่
คือ `${loUid}:${loEnteredAt}:${hiUid}:${hiEnteredAt}` ซึ่งทั้งสองฝั่งคำนวณได้เท่ากันจากแถวทะเบียน
คนแรกที่กด `fight` คำนวณแล้ว INSERT คนที่สองอ่าน `events_json` ก้อนเดิมกลับไปตรง ๆ
(ถ้าคำนวณใหม่ทั้งคู่ ผลจะเพี้ยนทันทีที่ฝ่ายใดฝ่ายหนึ่งเปลี่ยนอุปกรณ์ระหว่างนั้น)
คู่จากสแนปช็อตใช้ `snap:${snapshotId}:${uid}:${enteredAt}` — มีคนเห็นคนเดียวอยู่แล้ว

**หลังรบทุกครั้ง** เขียน `duel_snapshots` ของผู้เล่นหนึ่งแถว แล้ว prune ตาม `snapshotsPerPlayer`
— นี่คือสิ่งที่ทำให้ข้อ 2 ของ §5.2 มีของให้หยิบตั้งแต่วันแรก

### 8.5 `POST /api/world/leave` — ลบแถวทะเบียนของตัวเอง (กดออกจากหน้าแผนที่)

### 8.6 สองข้อที่ของจริงไม่ตรงกับ §8.1 — และทำไม PM รับไว้

**1. คนที่เข้าก่อนอาจถูก "อัปเกรด" คู่ดวล** §8.1 บอกว่าเลือกคู่ตอน `enter` แล้วจบ
แต่คนแรกที่เข้าโซนว่างย่อมไม่เจอใคร (ประกาศว่าไม่มีคู่ หรือได้สแนปช็อต) ส่วนคนที่สอง
เข้ามาแล้วเจอคนแรก — สองฝ่ายจึงคนละแมตช์ คนละบันทึก **เกณฑ์ W2 พังตั้งแต่ต้น**

ของจริงจึงเขียนคู่กลับไปที่แถวของอีกฝ่ายด้วย ผลคือคนที่เข้าก่อนอาจได้คู่ที่ดีกว่าที่ประกาศไว้
(ไม่มี → สแนปช็อต → คนจริง) **ส่วน EX ไม่ขยับ** — ตรวจแล้ว 50/50 รอบว่า `enter` กับ
`fight.announce` ตรงกันทุกไบต์ ที่ §4 ห้ามคือ "ดวงตัดสินว่าผ่านหรือไม่ผ่าน" ซึ่งการดวล
ไม่แตะแล้วตั้งแต่ §5.3 ถูกแก้ การเปลี่ยนนี้จึงเปลี่ยนได้แต่ในทางที่ดีขึ้น

**2. หนึ่ง `enter` สู้ได้ครั้งเดียว** §8.4 ไม่ได้สั่งให้กิน "ตั๋ว" แต่เพราะ seed คิดจากแถวทะเบียน
ที่ไม่ขยับ การยิง `fight` ซ้ำจึงได้ **รอบเดิมเป๊ะพร้อมของดรอปชุดเดิม** แล้วเข้ากระเป๋าใหม่ทุกครั้ง
กดเข้าใหม่แล้วฟาร์มไม่ผิด (สุ่มใหม่ เสี่ยงใหม่) แต่การคัดลอกผลที่รู้อยู่แล้วว่าชนะคือความเสี่ยงศูนย์
ซึ่งทำให้ทั้งระบบ EX และคำว่า "ผ่าน" กลวง · ตอนนี้ยิงซ้ำตอบ 409

**ยังไม่แก้ (บันทึกไว้):** การ์ดคู่ต่อสู้ของคนที่สองอ่านสดจากตารางตัวละคร ส่วนบันทึกการดวล
เป็นของที่แคชไว้ ถ้าอีกฝ่ายเลเวลอัพคั่นกลาง การ์ดจะบอกเลเวลใหม่บนการดวลที่คำนวณด้วยเลเวลเก่า
ทางแก้คือเก็บการ์ดลง `duel_matches` ไปพร้อมบันทึก — รอบหน้า
