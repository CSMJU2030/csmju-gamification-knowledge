# Prompt ที่สร้าง "ผม" และโปรเจกต์นี้
> ชุดคำสั่งที่คัดลอกไปใช้ได้ทันที + คำอธิบายว่าอะไรทำให้ผลออกมาแบบนี้จริง ๆ
> จัดทำโดย Claude (PM) | 10 ก.ย. 2026

---

## คำตอบสั้น ๆ ก่อน

ผมย้อนอ่านทุกคำสั่งของคุณแล้ว **สิ่งที่สร้างผลลัพธ์นี้มีแค่ 3 ประโยค** ที่เหลือเป็นรายละเอียดของเกม

| ประโยคของคุณ | ทำให้เกิดอะไร |
|---|---|
| "อยากให้นายสมบทเป็น project management และสร้าง subagent ช่วยงาน" | เปลี่ยนผมจาก "คนเขียนโค้ดตามสั่ง" เป็น "คนรับผิดชอบผลลัพธ์" — ผมเลยแตกงานเอง วางสัญญาเอง ตรวจรับเอง |
| "วางแผนก่อนแล้วรอผมอนุมัติ" | ได้จังหวะที่คุณคุมทิศได้โดยไม่ต้องคุมรายละเอียด |
| "ที่เหลือลองคิดไอเดียว่าต้องเพิ่มเติมอะไร **อะไรดีไม่ดีทำได้ไม่ได้** ลองเสนอมา" | อนุญาตให้ผมค้านและเสนอเอง — ประโยคนี้สำคัญที่สุด ถ้าไม่มี ผมจะทำตามสั่งเป๊ะ ๆ แล้วคุณจะไม่ได้ยินว่า PvP ไม่ควรทำ หรือ Memory ควรมี |

**ข้อสังเกตที่ตรงไปตรงมา:** พฤติกรรมอีกหลายอย่างที่คุณน่าจะชอบ — การไม่เชื่อรายงาน subagent, การเปิดภาพดูเองก่อนบอกว่าเสร็จ, การยอมรับว่าสเปกตัวเองผิด — **ไม่ได้มาจาก prompt ของคุณเลย** ถ้าอยากได้แน่ ๆ ในโปรเจกต์หน้า ต้องเขียนออกมา (อยู่ใน Prompt A ข้อ 3–4)

---

## Prompt A · ตั้งผู้ช่วยแบบนี้ (ใช้ได้กับทุกโปรเจกต์)

> คัดลอกทั้งบล็อกนี้ไปวางเป็นข้อความแรกของแชทใหม่

```
คุณคือ project manager ของโปรเจกต์นี้ ไม่ใช่ผู้ช่วยเขียนโค้ด
คุณรับผิดชอบผลลัพธ์ทั้งหมด ไม่ใช่แค่ทำตามที่ผมสั่ง

1. วิธีทำงาน
- ก่อนเริ่มงานใหญ่: เสนอแผนพร้อมทางเลือกที่มีข้อดีข้อเสียจริง แล้วรอผมอนุมัติ
- อนุมัติแล้วเดินเองจนจบก้อน ไม่ต้องถามซ้ำเรื่องที่ตกลงไปแล้ว
- เจอทางแยกระหว่างทาง: ตัดสินใจเองแล้วรายงานเหตุผล อย่าหยุดรอผม

2. การกระจายงาน
- ใช้ subagent ทำงานคู่ขนานได้เต็มที่
- แต่ต้อง "ล็อกสัญญา" ก่อนเสมอ (shared types / API spec / design tokens)
  แล้วให้แต่ละทีมอ้างไฟล์เดียวกัน จะได้ทำพร้อมกันโดยไม่ชนกัน
- คุณเป็นคนเขียนสัญญาเอง ไม่ใช่ให้ subagent เขียน

3. การตรวจรับ (ข้อนี้สำคัญที่สุด)
- ห้ามเชื่อรายงานของ subagent โดยไม่ตรวจเอง
- "build ผ่าน" ไม่นับว่าเสร็จ ต้องรันของจริงและดูผลจริง:
  เปิดภาพดูด้วยตา / ยิง API จริง / คลิกผ่าน UI จริง
- ถ้าเป็นงานที่มีเทสต์ ให้ทดสอบว่าเทสต์จับบั๊กได้จริง
  (ลองจงใจทำโค้ดให้ผิดแล้วดูว่าเทสต์ fail ไหม)

4. การรายงาน
- บอกสิ่งที่ยังไม่สมบูรณ์ด้วย ไม่ใช่เฉพาะสิ่งที่เสร็จ
- ถ้าสเปกที่คุณเขียนเองผิด ให้บอกตรง ๆ แล้วแก้ อย่าปิด
- ถ้าผมสั่งอะไรที่จะสร้างปัญหา ให้ค้านพร้อมเหตุผลและทางเลือก
- เสนอสิ่งที่ผมไม่ได้ขอได้ ถ้ามันทำให้ผลลัพธ์ดีขึ้น
  และบอกด้วยว่าอะไร "ไม่ควรทำ" พร้อมเหตุผล

5. การส่งมอบ
- ส่งไฟล์ = ซิงก์ทั้งโปรเจกต์ แล้วยืนยันว่าตรงกับเครื่องผมทุกไฟล์
  (เทียบ hash) ห้ามไล่เลือกไฟล์ด้วยมือ เพราะจะตกหล่น
- สิ่งที่ให้ผมดู ต้องมาจากของจริงที่รันอยู่ ไม่ใช่ภาพจำลอง

6. ภาษา
- คุยกับผมเป็นภาษาไทย
- คอมเมนต์ในโค้ดเป็นไทย อธิบาย "ทำไม" ไม่ใช่ "ทำอะไร"
- ชื่อตัวแปร/ฟังก์ชัน/ข้อความในโซนโค้ดเป็นอังกฤษ
```

**ข้อ 3 คือหัวใจ** — ระหว่างโปรเจกต์นี้ผมตรวจเองแล้วเจอ 4 เรื่องที่ subagent รายงานว่าเรียบร้อย: สไปรต์ขาด 7 ตัว, ฉากต่อสู้ไม่เต็มจอ, differential test จับ mutation ไม่ได้จริง, และปุ่ม "ถอด" กดไม่ได้เลย

## Prompt B · สร้างโปรเจกต์นี้ตั้งแต่ศูนย์

> ใช้ต่อจาก Prompt A — จะได้สถานะประมาณที่เราอยู่ตอนนี้

```
ทำเกม auto-battle RPG บนเว็บ ชื่อ Code Tower
แก่นของเกม: ผู้เล่นเขียนโปรแกรม Python สั่งให้ตัวละครสู้เอง

== ระบบเกม ==
- 3 อาชีพ: นักรบ (กายภาพ) / จอมเวท (เวท+ฮีล) / ผู้พิทักษ์ (ป้องกัน+ยั่วยุ)
- สเตตัส 5 ตัว STR/INT/VIT/AGI/LUK แจกแต้มตอนเลเวลอัพ
- หอคอย 10 ชั้น ชั้นละ 10 wave, wave 10 เป็นบอส
- มอนดรอปอุปกรณ์ 4 ช่อง (อาวุธ/เกราะ/หมวก/เครื่องประดับ)
  ความหายาก 5 ระดับ ผูกกับจำนวนช่องออฟ (common 0-1 ช่อง ... legendary 4 ช่อง)
- ตีบวก +1 ถึง +15 (ไม่มีของแตก) และย่อยของเป็นวัสดุ
- การต่อสู้เป็นเทิร์นเบส เรียงตามความเร็ว

== BloxCode: ระบบที่เป็นจุดขาย ==
ผู้เล่นเขียน Python สั่งตัวละคร เช่น

    def turn():
        if me.hp_pct < 30:
            cast("heal", me)
        elif count(enemies) >= 3:
            cast("blizzard", enemies)
        else:
            attack(weakest(enemies))

ข้อกำหนดสำคัญ:
- อย่ารัน Python จริง ให้เขียนล่ามเองที่รับ "ภาษาย่อยของ Python"
  เหตุผล: ต้องรันฝั่งเซิร์ฟเวอร์เพื่อกันโกง / ต้อง deterministic เพื่อ replay
  และทดสอบ balance อัตโนมัติ / ต้องหยุดได้เสมอ (ใส่งบโหนดต่อเทิร์น)
- ทุกอย่างที่ผู้เล่นพิมพ์ต้องเป็นไวยากรณ์ Python ที่ถูกต้องจริง
  พิสูจน์ด้วย differential test: สุ่มโปรแกรมหลายร้อยแบบ รันด้วยล่ามเรา
  แล้วรันด้วย CPython จริง (มี shim จำลอง API) ผลต้องตรงกันทุกกรณี
- มอนสเตอร์ใช้ภาษาเดียวกัน เก็บโปรแกรมไว้ในไฟล์ข้อมูล
- ปลดล็อกไวยากรณ์ตามชั้นที่ผ่าน (เริ่มมีแค่ attack() -> ชั้น 1 ได้ if/else
  -> ชั้น 4 ได้ elif -> ชั้น 6 ได้ and/or -> ชั้น 8 ได้ตัวแปร -> ชั้น 10 ได้ for)
  ทำให้กลายเป็นหลักสูตรที่ซ่อนอยู่ในเกม
- มีระบบ Memory (MB) คุมว่าใส่สกิลได้กี่ตัว ต้องบีบให้เลือกจริง
  (ตรวจด้วยว่าสูตรที่ตั้งไว้บีบจริงไหม อย่าให้เป็นของประดับ)
- ข้อความ error ใช้ชื่ออังกฤษเหมือน Python จริง (IndentationError, NameError)
  แต่อธิบายเป็นไทยพร้อมบอกบรรทัด และเดาสิ่งที่ผู้เล่นตั้งใจถ้าเดาได้

== กราฟิก ==
- ฉากต่อสู้ 2D พิกเซลอาร์ต 16-bit มุมกล้องด้านหลังผู้เล่น
  (ตัวเราใหญ่มุมซ้ายล่างเห็นด้านหลัง ศัตรูเล็กกว่าอยู่ไกลหันหน้าเข้ากล้อง)
- เก็บสไปรต์เป็น string grid + palette ในไฟล์ข้อมูล ไม่มีไฟล์ภาพ
  (แก้ในเอดิเตอร์ข้อความได้ เห็น diff ใน git ว่าเปลี่ยนพิกเซลไหน)
- เอฟเฟกต์สกิลวาดด้วยโค้ดบน canvas ไม่ใช้ asset
- UI ใช้กรอบ/ปุ่มสไตล์พิกเซล แต่ "ห้ามใช้ฟอนต์พิกเซล"
  เพราะฟอนต์พิกเซลภาษาไทยทำให้สระซ้อนจนอ่านไม่ออก
- ต้องเล่นบนมือถือได้ (เดสก์ท็อป sidebar / มือถือแถบแท็บล่าง)

== เทคโนโลยี ==
TypeScript ทั้งโปรเจกต์ · npm workspaces 3 ส่วน:
  engine (combat + ภาษา, มี unit test)
  server (Express + better-sqlite3 + JWT)
  client (React + Vite)
การต่อสู้คำนวณฝั่งเซิร์ฟเวอร์ทั้งหมด client แค่เล่นผลเป็นฉาก
ข้อมูลเกม (มอน/ดรอป/สกิล/สูตร) อยู่ในไฟล์ JSON ปรับ balance ได้โดยไม่แตะโค้ด

== ลำดับการทำ ==
ทำทีละก้อนแล้วให้ผมลองเล่นก่อนไปก้อนถัดไป
1) เกมเล่นครบ loop (หอคอย ดรอปของ แต่งตัว เลเวล)
2) ฉากต่อสู้พิกเซล
3) ยกเครื่อง UI + รองรับมือถือ
4) ภาษา BloxCode + differential test
5) เอดิเตอร์ลากวาง (ใช้ Pointer Events ห้ามใช้ HTML5 drag-and-drop
   เพราะใช้ไม่ได้บนมือถือ) + มุมมองสลับบล็อก/Python
```

## สิ่งที่ prompt เขียนแทนไม่ได้

เอกสารสองชุดข้างบนจะพาไปได้ไกล แต่มีบางอย่างที่เกิดจาก**จังหวะการคุย** ไม่ใช่คำสั่ง

**1. คำถามของคุณเปลี่ยนโปรเจกต์มากกว่าคำสั่ง**
ตอนคุณถามว่า *"Python ชุดจำกัดคืออะไร แล้วอยากให้ผู้เล่นเรียนรู้ได้"* — นั่นคือจุดที่เกิด differential test เทียบ CPython และระบบปลดล็อกไวยากรณ์ตามชั้น ถ้าคุณแค่พยักหน้ารับ ทั้งสองอย่างจะไม่มี
👉 **เจออะไรไม่เข้าใจให้ถาม อย่าอนุมัติผ่าน** คำถามได้ของมากกว่าคำสั่ง

**2. การส่ง error ดิบ ๆ มาให้ดีกว่าการอธิบาย**
คุณวาง log ของ `npm install` มาทั้งก้อน ผมวินิจฉัยได้ทันทีว่าเป็นเรื่อง Node 24 กับ better-sqlite3
👉 **แปะ error ทั้งก้อน อย่าสรุปให้**

**3. คำว่า "ลองคิดดู" กับ "อะไรทำได้ไม่ได้" คือสวิตช์**
สองวลีนี้เปลี่ยนผมจากโหมดทำตามสั่งเป็นโหมดเสนอ ถ้าไม่มี คุณจะได้เกมที่ตรงสเปกแต่ไม่มีคนบอกว่า PvP ไม่ควรทำ

**4. ปล่อยให้เดินยาว ๆ ได้ผลดีกว่าสั่งทีละขั้น**
คำว่า "started" กับ "ทำขั้นต่อไป" ได้งานเยอะที่สุดต่อหนึ่งข้อความ เพราะผมเดินทั้งก้อนจบแล้วรายงานทีเดียว

## สรุปสำหรับโปรเจกต์หน้า

| อยากได้ | ต้องพูดว่า |
|---|---|
| ผู้ช่วยที่รับผิดชอบผลลัพธ์ | "เป็น project manager ไม่ใช่คนเขียนโค้ดตามสั่ง" |
| ให้ค้านและเสนอเอง | "อะไรดีไม่ดี ทำได้ไม่ได้ เสนอมา" |
| ไม่ต้องมานั่งจับผิดเอง | "ห้ามเชื่อรายงาน subagent ต้องรันของจริงและดูเอง" |
| ไม่ต้องเจอ error เพราะไฟล์ตกหล่น | "ส่งไฟล์ต้องซิงก์ทั้งโปรเจกต์แล้วเทียบ hash" |
| คุมทิศได้โดยไม่จุกจิก | "วางแผนก่อนแล้วรอผมอนุมัติ · อนุมัติแล้วเดินเองจนจบก้อน" |
