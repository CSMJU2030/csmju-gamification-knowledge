## 2. BloxCode — ทำไมเป็น "Python ชุดจำกัด" ไม่ใช่ Python จริง

### ข้อเสนอ: ภาษาย่อยของ Python (Python subset) ที่เราแปลเอง
ผู้เล่นเขียนโค้ดที่**หน้าตาและกฎไวยากรณ์เป็น Python จริงทุกประการ** (indent, `if/elif/else`, `and/or/not`, การเรียกฟังก์ชัน) แต่ฝั่งเราเขียน **tokenizer + parser + evaluator ของเราเอง (TypeScript)** ไม่ได้รัน Python runtime จริง

**เหตุผล 4 ข้อ:**

1. **ความปลอดภัย** — โค้ดผู้เล่นรันบนเซิร์ฟเวอร์ (เพราะการต่อสู้ต้องคำนวณฝั่งเซิร์ฟเวอร์เพื่อกันโกง) การรัน Python จริงจากผู้ใช้ = ช่องโหว่ระดับยึดเครื่อง ต่อให้ sandbox ก็ยังเสี่ยงและต้องดูแลตลอดอายุโปรเจกต์
2. **Deterministic** — เกมเราการันตีว่า seed เดิม = ผลเดิม (ใช้ทำ replay/แชร์ build/ทดสอบ balance อัตโนมัติ) ถ้ารัน Python จริงจะควบคุมเวลา/หน่วยความจำไม่ได้ ระบบ replay พังทันที
3. **หยุดได้เสมอ** — evaluator ของเราใส่ "งบ" ได้ เช่น 300 โหนดต่อเทิร์น เกินแล้วตัดจบ → ไม่มีทาง infinite loop ล่มเซิร์ฟเวอร์
4. **ซิงก์กับบล็อกได้** — เพราะเรามี AST ของเราเอง จึงแปลงบล็อก ⟷ ข้อความได้สองทางแบบไม่มีทางเพี้ยน (ถ้าใช้ Python จริงจะแปลงกลับเป็นบล็อกไม่ได้)

> ผู้เล่นจะไม่รู้สึกต่างเลย เพราะสิ่งที่เขาพิมพ์คือ Python ที่ถูกต้องตามหลักภาษา — แค่เรารองรับเฉพาะคำสั่งที่เกมใช้จริง ถ้าอนาคตอยากได้ Python เต็มรูปแบบฝั่ง client (Pyodide) ค่อยเพิ่มเป็นโหมดพรีวิวได้โดยไม่กระทบของเดิม

### รูปแบบโปรแกรม
เกมเรียก `turn()` หนึ่งครั้งเมื่อถึงเทิร์นของตัวละคร:

```python
# เกมเรียก turn() ให้ 1 ครั้งต่อเทิร์นของเรา
def turn():
    if me.hp_pct < 30:
        cast("heal", me)
    elif count(enemies) >= 3:
        cast("blizzard", enemies)
    else:
        attack(weakest(enemies))
```

### API ที่ให้ผู้เล่นใช้ (เฟส 2B)
| กลุ่ม | รายการ |
|---|---|
| ตัวแปร | `me` (`.hp_pct` `.mp_pct` `.hp` `.mp` `.level` `.atk`), `enemies`, `allies`, `turn_no` |
| เลือกเป้า | `weakest(l)` `strongest(l)` `fastest(l)` `random_of(l)` `count(l)` |
| เงื่อนไข | `has_buff(name)` `has_debuff(name)` `can_cast(name)` |
| การกระทำ | `attack(t)` `cast(name, t)` `defend()` `wait()` |
| ไวยากรณ์ | `if/elif/else`, `and/or/not`, เปรียบเทียบ `< <= > >= == !=`, `+ - * /`, ตัวแปรท้องถิ่น, `for x in enemies:` (วนได้สูงสุดตามจำนวนสมาชิกจริง) |

**ไม่รองรับ (และจะฟ้อง error ชัดเจนเป็นภาษาไทย):** `import`, `while`, `def` อื่นนอกจาก `turn()`, `open`, `eval`, การเข้าถึง attribute นอกรายการ

### กฎการทำงานสำคัญ
- ต้องจบเทิร์นด้วยการกระทำ 1 อย่าง — ถ้าโค้ดวิ่งจบโดยไม่เรียก action ใด ตัวละครจะ `attack(weakest(enemies))` อัตโนมัติ (กันผู้เล่นยืนเฉยเพราะเขียนพลาด)
- เรียก action ซ้อนหลายครั้ง = นับเฉพาะครั้งแรก (เทิร์นละ 1 การกระทำ)
- `cast` สกิลที่ MP ไม่พอ หรือยังไม่มีบล็อกนั้น = คำสั่งนั้นถูกข้าม (ไม่เสียเทิร์น) และขึ้นเตือนในบันทึกการต่อสู้
- **มอนสเตอร์ใช้ระบบเดียวกัน** — AI ของมอนคือโปรแกรม BloxCode ที่เราเขียนไว้ใน `gamedata.json` (โปร่งใส ปรับ balance ง่าย และผู้เล่นดูโค้ดมอนได้ = เรียนรู้จากมัน)

### มุมมองบล็อก ⟷ Python
- บล็อกและข้อความคือ **AST ชุดเดียวกัน** คนละมุมมอง สลับได้ทุกเมื่อ ไม่มีข้อมูลหาย
- ผู้เล่นใหม่ต่อบล็อก ผู้เล่นเก่งพิมพ์เอา — โตไปกับผู้เล่น
- แก้ในมุมมองข้อความแล้วมี syntax error → บล็อกจะไม่อัปเดตจนกว่าจะแก้ถูก (แสดง error ใต้บรรทัดที่ผิด)

## 3. บล็อก = ของดรอป (แนวคิดที่รวมสองระบบเข้าด้วยกัน)

**มอนสเตอร์ดรอป "ฟังก์ชัน" ให้คุณเรียกใช้** — `cast("poison_sting", ...)` จะใช้ได้ก็ต่อเมื่อคุณมีบล็อก `poison_sting` แล้ว
พูดอีกแบบ: **ของดรอป = API ที่คุณปลดล็อก** ซึ่งเข้าธีมเกมนี้พอดี และทำให้ลูปฟาร์มมีสองชั้น

| ชั้นการฟาร์ม | ได้อะไร | ความรู้สึก |
|---|---|---|
| อุปกรณ์ (มีแล้ว) | ตัวเลขแรงขึ้น | ค่อย ๆ เก่งขึ้น |
| **บล็อก (ใหม่)** | ท่าใหม่ + แอนิเมชันใหม่ + วิธีเล่นใหม่ | ปลดล็อกความเป็นไปได้ |

### กติกาการดรอป
- มอนแต่ละตัวมีตารางดรอปบล็อกตามธีมของมัน (เมจมืด → `dark_bolt`, โกเลม → `stone_skin`, ฮาร์ปี้ → `double_slash`)
- บอสประจำชั้นดรอปบล็อกแรร์ประจำชั้นนั้น (เช่น บอสชั้น 9 → `meteor`)
- บล็อกมีระดับความหายาก 5 ระดับ ใช้สีเดียวกับอุปกรณ์
- **บล็อกซ้ำ** → อัพเกรดบล็อก (แรงขึ้น / กิน MB น้อยลง / แอนิเมชันอลังขึ้น) หรือย่อยเป็น **Code Fragment** เอาไปคราฟต์บล็อกที่อยากได้
- บล็อกพื้นฐาน (`attack` `defend` `if` `weakest` ฯลฯ) มีให้ตั้งแต่ต้น — ไม่มีทางเล่นไม่ได้
- สกิลประจำอาชีพเดิม 9 ตัว กลายเป็นบล็อกที่ได้ฟรีตามเลเวล (ของเดิมไม่หาย)

### ความสามารถแบบใหม่ที่บล็อกดรอปจะมี (เฟส 2C)
| ประเภท | ตัวอย่าง | ผล |
|---|---|---|
| ติดสถานะ | `poison_sting` | พิษ เสียเลือดต่อเทิร์น 3 เทิร์น |
| ควบคุม | `stun_bash` | มึน ข้ามเทิร์นถัดไป 1 ครั้ง |
| บัฟ | `war_cry` | ATK ทีม +20% 3 เทิร์น |
| หลายฮิต | `double_slash` | ตี 2 ครั้ง ครั้งละ 70% |
| ดูดเลือด | `blood_edge` | ตี + ฟื้น HP 30% ของดาเมจ |
| ป้องกัน | `stone_skin` | DEF +50% 2 เทิร์น |

### Memory (MB) — ตัวคุม balance
ตัวละครมี MB จำกัด (เริ่ม 10 MB, +1 ทุก 2 เลเวล) บล็อกแต่ละตัวกิน MB ต่างกัน (`attack` 0 MB, `firebolt` 3 MB, `meteor` 8 MB) → **มีบล็อกครบไม่ได้แปลว่าใช้ได้หมด ต้องออกแบบ build**
นี่คือหัวใจของความสนุกสาย programming: optimize ภายใต้ข้อจำกัด และเป็นปุ่มปรับ balance ที่เราหมุนได้ง่ายมาก (แก้ตัวเลขในไฟล์ข้อมูล)

## 4. ฉากต่อสู้ 2D มุมกล้องด้านหลัง

### แนวทางกราฟิก: พิกเซลอาร์ต 16-bit จริง
- ความละเอียดฐาน **256×160** ขยาย 5 เท่าแบบ nearest-neighbor → 1280×800 คมทุกพิกเซล
- ตัวเราอยู่ใกล้กล้อง (สไปรต์ใหญ่ เห็นด้านหลัง มุมซ้ายล่าง) ศัตรูอยู่ไกล (สไปรต์เล็ก หันหน้าเข้ากล้อง ยืนบนแท่น)
- พื้นมีเส้นสอบเข้าหาจุดรวมสายตา = ให้ความลึกโดยไม่ต้องใช้ 3D

### Sprite pipeline (ข้อเสนอสำคัญ)
**ไม่เก็บไฟล์ภาพ binary ในรีโปเลย** — สไปรต์เก็บเป็น **string grid + palette** ในไฟล์ข้อมูล แล้วเรนเดอร์ด้วย `<canvas>` ตอนรัน

```jsonc
{ "palette": { "o": "#141024", "n": "#54ad68", "e": "#f6f6fc" },
  "frames": { "idle": ["..o..o..", ".onnnno.", "onneenno"] } }
```

ข้อดี: แก้สไปรต์ได้ในเอดิเตอร์ข้อความ, เห็น diff ใน git ว่าเปลี่ยนพิกเซลไหน, ไม่ต้องมี asset pipeline, ไฟล์เล็กมาก, subagent สร้าง/แก้ได้เอง
ผมได้ **ทดสอบ pipeline นี้จริงแล้ว** — ภาพ mockup ที่แนบมาเรนเดอร์จากวิธีนี้ทั้งหมด

### สถานะแอนิเมชันต่อตัวละคร
`idle` (หายใจ 2 เฟรม) · `act` (ก้าวเข้าฟัน / ยกไม้เท้าร่าย) · `hit` (สั่น + กะพริบแดง) · `down` (ล้ม/จมลงพื้น)

### แอนิเมชันเอฟเฟกต์ — วาดด้วยโค้ด ไม่ใช้สไปรต์
แต่ละบล็อกมี `animation` id ผูกกับฟังก์ชันวาดบน canvas:

| animation | ภาพ |
|---|---|
| `slash` | รอยฟันโค้งขาวพาดตัวเป้า |
| `projectile_fire` | ลูกไฟพุ่งข้ามสนาม + หางไฟ + ระเบิด |
| `rain_ice` | เกล็ดน้ำแข็งตกทั่วจอ + จอแวบฟ้า |
| `spin` | ตัวหมุน + วงลมตัดศัตรูทุกตัว |
| `heal_ring` | วงแสงเขียวลอยขึ้น |
| `shield_dome` | โดมโล่ฟ้าครอบตัว |
| `poison_cloud` | หมอกม่วงลอยรอบเป้า |
| `impact_stun` | ดาวหมุนรอบหัว + จอสั่น |

การเพิ่มบล็อกใหม่ในอนาคต = เขียนฟังก์ชันวาดเพิ่ม 1 ตัว ไม่ต้องทำ asset

### สิ่งที่ทำให้ฉากนี้ "เป็นเกมนี้"
**แถบโค้ดด้านล่างไฮไลต์บรรทัดที่กำลังทำงาน** ระหว่างต่อสู้ — ผู้เล่นเห็นว่าโปรแกรมตัวเองกำลังตัดสินใจอะไร ทำให้เข้าใจว่าทำไมแพ้/ชนะ และรู้ว่าต้องแก้บรรทัดไหน (นี่คือ feedback loop ที่ทำให้เกมสอนการเขียนโปรแกรมโดยไม่ต้องมีบทเรียน)

## 5. แผนงาน

### ก้อน 2A — ฉากต่อสู้พิกเซล (เริ่มก่อน)
| งาน | ผู้รับผิดชอบ |
|---|---|
| ระบบสไปรต์ (schema + renderer canvas + ตัวช่วยขยายภาพ) | `ui-dev` |
| สไปรต์ 3 อาชีพ (มุมหลัง) × 4 สถานะ | `pixel-artist` (subagent ใหม่) |
| สไปรต์ 9 มอนสเตอร์ + 10 บอส (บอสใช้ palette swap + ขนาดใหญ่ + มงกุฎ) × 3 สถานะ | `pixel-artist` |
| ฉาก: พื้น perspective, แท่นยืน, ท้องฟ้า, HUD ใหม่ | `ui-dev` |
| ตัวเล่นแอนิเมชัน 8 เอฟเฟกต์ของสกิลเดิม | `ui-dev` |
| เพิ่ม `animationId` ในข้อมูลสกิล + ส่งผ่าน event | `engine-dev` (งานเล็ก) |

**เกณฑ์รับงาน:** เล่นชั้น 1–10 ได้ครบ เห็นแอนิเมชันครบทุกสกิล เฟรมเรตนิ่งที่ 60fps ปุ่ม x1/x2/x4/ข้าม ยังทำงาน และ**ระบบเดิมไม่พัง** (API ไม่เปลี่ยน)

### ก้อน 2B — BloxCode editor
| งาน | ผู้รับผิดชอบ |
|---|---|
| ภาษา: tokenizer + parser + AST + evaluator (มีงบโหนด) พร้อม unit test | `engine-dev` |
| แปลง AST ⟷ บล็อก และ AST ⟷ ข้อความ Python | `engine-dev` |
| ย้าย AI มอนสเตอร์มาใช้ BloxCode ใน `gamedata.json` | `engine-dev` |
| API: บันทึก/ตรวจโปรแกรม, ตรวจ MB, ข้อความ error ภาษาไทย | `backend-dev` |
| UI: เอดิเตอร์บล็อกลากวาง + เอดิเตอร์ข้อความ syntax highlight + สลับมุมมอง + มาตร MB | `ui-dev` |
| ไฮไลต์บรรทัดที่ทำงานในฉากต่อสู้ | `ui-dev` |

**เกณฑ์รับงาน:** เขียนโปรแกรมได้ทั้ง 2 มุมมอง สลับไปกลับแล้วโค้ดไม่เพี้ยน, โปรแกรมพังไม่ทำให้เซิร์ฟเวอร์ล่ม, กฎเดิมของผู้เล่นถูกแปลงเป็น BloxCode อัตโนมัติ (ไม่มีใครเสียของ), มอนสเตอร์สู้ด้วย BloxCode แล้ว balance ยังผ่านเทสต์เดิม

### ก้อน 2C — บล็อกเป็นของดรอป
| งาน | ผู้รับผิดชอบ |
|---|---|
| ระบบสถานะ (พิษ/มึน/บัฟ/ดีบัฟ) + หลายฮิต + ดูดเลือด ใน engine | `engine-dev` |
| บล็อกใหม่ 12–15 ตัว + ตารางดรอปต่อมอน + ความหายาก | `game-designer` |
| API: กล่องบล็อก, อัพเกรด, ย่อย, คราฟต์ | `backend-dev` |
| UI: แท็บกล่องบล็อก + หน้าอัพเกรด/คราฟต์ + แอนิเมชันบล็อกใหม่ | `ui-dev` |
| ปรับ balance ใหม่ทั้งหมด (มอนมีสถานะแล้ว ยากขึ้น) | `qa` + `engine-dev` |

## 7. ให้ผู้เล่นได้เรียน Python จริง ๆ (เป้าหมายหลักของเกม)

### 7.1 "Python ชุดจำกัด" คืออะไรกันแน่

ปกติเวลารันโปรแกรม Python จะมี **ล่าม (interpreter)** ชื่อ CPython อ่านโค้ดแล้วทำตาม
สิ่งที่เราจะทำคือ **เขียนล่ามของเราเอง** (ประมาณ 600–900 บรรทัด TypeScript) ที่อ่านไวยากรณ์ Python เหมือนกัน แต่รองรับเฉพาะคำสั่งที่เกมใช้

เทียบให้เห็นภาพ: **MicroPython** ที่รันบนบอร์ดไมโครคอนโทรลเลอร์ก็เป็นแบบนี้ — มันคือ Python จริง เขียนเหมือนกันทุกอย่าง แค่ไม่มีไลบรารีครบเท่าบนคอม ไม่มีใครบอกว่า "คนเขียน MicroPython ไม่ได้เขียน Python"

**สิ่งที่เหมือน Python จริง 100%** (คือสิ่งที่ผู้เล่นจะได้เรียน):

```python
def turn():                          # นิยามฟังก์ชัน + เครื่องหมาย :
    if me.hp_pct < 30:               # if + ตัวดำเนินการเปรียบเทียบ
        cast("heal", me)             # เรียกฟังก์ชัน + argument + string
    elif count(enemies) >= 3 and me.mp_pct > 50:   # elif + and
        cast("blizzard", enemies)
    else:
        target = weakest(enemies)    # ตัวแปร
        attack(target)
```

การเยื้องบรรทัด (indentation) มีความหมาย, `:` ปิดท้ายบล็อก, `==` ไม่ใช่ `=`, ลำดับการทำงานบนลงล่าง, `and/or/not`, ฟังก์ชันซ้อนฟังก์ชัน — **ทั้งหมดนี้คือ Python แท้** ผู้เล่นที่เข้าใจตรงนี้ เปิด VS Code เขียน Python ได้ทันที

**สิ่งที่ไม่มี:** `import`, ไลบรารีมาตรฐาน, class, ไฟล์/เน็ตเวิร์ก, `while` (กันลูปไม่รู้จบ) — ของพวกนี้ไม่มีความหมายในฟังก์ชันตัดสินใจ 1 เทิร์นอยู่แล้ว และเป็นบทเรียนถัดไปนอกเกม

### 7.2 การรับประกันว่า "ที่เรียนในเกม = Python จริง"

เราจะไม่พูดลอย ๆ แต่**ทดสอบอัตโนมัติ**: ใน CI สุ่มสร้างโปรแกรมที่ถูกไวยากรณ์หลายพันแบบ แล้ว

1. รันด้วยล่ามของเรา (TypeScript)
2. รันด้วย **CPython จริง** โดยมีไฟล์ `api.py` จำลอง `me` / `enemies` / `attack()` ให้เหมือนกัน
3. **ผลลัพธ์ต้องตรงกันทุกกรณี**

ถ้าไม่ตรง = ล่ามเราผิด ต้องแก้ ไม่ใช่ปล่อยผ่าน กติกานี้ทำให้ภาษาของเรา "เพี้ยนจาก Python" ไม่ได้เลย และเป็นหลักประกันเรื่องการเรียนรู้ที่ตรวจสอบได้จริง

> ผลพลอยได้: ถ้าวันหนึ่งอยากเปลี่ยนไปใช้ Python จริง ก็ทำได้โดยผู้เล่นไม่ต้องแก้โค้ดสักบรรทัด

### 7.3 หัวใจ: ทำให้ "ภาษา" เป็นของดรอปด้วย

แทนที่จะให้ผู้เล่นเจอไวยากรณ์ทั้งหมดตั้งแต่นาทีแรก (ท่วมท้น เลิกเล่น) เราปลดล็อกทีละอย่างตามความคืบหน้า — **กลายเป็นหลักสูตรที่ซ่อนอยู่ในเกม**

| ปลดล็อกเมื่อ | ได้ไวยากรณ์ | ได้เรียนเรื่อง |
|---|---|---|
| เริ่มเกม | `def turn():` · `attack()` · การเยื้อง | ฟังก์ชันและ indentation |
| ผ่านชั้น 1 | `if` / `else` · `<` `>` | เงื่อนไข |
| ผ่านชั้น 2 | `cast("ชื่อ", เป้า)` · string | argument และ string |
| ผ่านชั้น 4 | `elif` | หลายทางเลือก |
| ผ่านชั้น 6 | `and` `or` `not` | ตรรกะบูลีน |
| ผ่านชั้น 8 | ตัวแปร `t = weakest(enemies)` | ตัวแปรและการใช้ซ้ำ |
| ผ่านชั้น 10 | `for x in enemies:` | การวนซ้ำ |
| ผ่านชั้น 13 | `len()` · เลขคณิต `+ - * /` | ข้อมูลและการคำนวณ |
| ผ่านชั้น 15 | `def ฟังก์ชันของตัวเอง():` | แยกฟังก์ชัน / นามธรรม |

ผู้เล่นจะรู้สึกว่า "ได้ท่าใหม่" ไม่ใช่ "ต้องเรียนบทที่ 5" — แต่ผ่านชั้น 15 แล้วเขาเขียนโปรแกรมเป็นจริง ๆ

### 7.4 ฟีเจอร์ช่วยเรียนรู้ (เรียงตามความคุ้มค่า)

| # | ฟีเจอร์ | ทำไมได้ผล | ต้นทุน |
|---|---|---|---|
| 1 | **ไฮไลต์บรรทัดที่กำลังทำงาน** ระหว่างต่อสู้ (มีในแผนแล้ว) | เห็นความเชื่อมโยง "โค้ด → ผลลัพธ์" ซึ่งเป็นสิ่งที่ยากที่สุดของการเริ่มเขียนโปรแกรม | ต่ำ |
| 2 | **ดูโค้ดของมอนสเตอร์ได้** หลังจบการต่อสู้ | คนเรียนเขียนโปรแกรมจากการ *อ่าน* โค้ดมากกว่าการเขียน — และตอบคำถาม "ทำไมมันฮีลตอนนั้น" ได้ด้วยตัวเอง | ต่ำ (มอนใช้ระบบเดียวกันอยู่แล้ว) |
| 3 | **รายงานหลังจบ**: "บรรทัด 5 ไม่เคยถูกใช้เลย" / "ใช้ heal ตอน HP 90% ไป 6 ครั้ง" | สอนเรื่อง dead code และตรรกะผิดโดยไม่ต้องมีคนสอน | ต่ำ-กลาง |
| 4 | **ห้องซ้อม** — สู้กับหุ่นทดลองที่เลือกเองได้ ไม่เสียอะไร ดูผลทันที | ความเร็วในการลองผิดลองถูกคือหัวใจของการเรียนเขียนโปรแกรม | กลาง |
| 5 | **ด่านปริศนา** — โจทย์ตายตัว เช่น "ชนะใน 5 เทิร์น ใช้ไม่เกิน 6 MB" | บังคับให้เข้าใจแนวคิดเฉพาะเรื่อง (แบบเกม Zachtronics) และเป็นคอนเทนต์ที่ทำเพิ่มง่าย | กลาง |
| 6 | **ปุ่มดาวน์โหลดเป็นไฟล์ `.py`** พร้อมตัวจำลองเล็ก ๆ ให้รันบนคอมจริงได้ | ปิดวงจร "ที่เล่นในเกม = โค้ดที่รันได้จริง" ซึ่งเป็นช่วงเวลาที่ผู้เล่นเชื่อว่าตัวเองเขียนโปรแกรมเป็น | ต่ำ |
| 7 | ข้อความ error เลียนแบบ Python จริง (`IndentationError`, `NameError`) แต่อธิบายเป็นไทยใต้บรรทัด | เจอ error เดียวกันนี้ตอนไปเขียน Python จริง จะไม่ตกใจ | ต่ำ |

**ข้อเสนอของ PM:** ใส่ข้อ 1, 2, 6, 7 ตั้งแต่ก้อน 2B (ต้นทุนต่ำทั้งหมด ได้ผลสูง) แล้วเก็บข้อ 3, 4, 5 ไว้เป็นก้อน 2D หลังระบบนิ่ง

### 7.5 สิ่งที่ผู้เล่นจะยังไม่ได้จากเกมนี้
ไลบรารีมาตรฐาน · การจัดการไฟล์/เน็ตเวิร์ก · class และ OOP · การติดตั้งแพ็กเกจ · การดีบักโปรแกรมใหญ่
เกมนี้สอน **ตรรกะและไวยากรณ์พื้นฐาน** ซึ่งเป็นด่านที่คนล้มเลิกมากที่สุด — ผ่านตรงนี้ได้ ที่เหลือเรียนต่อเองไม่ยาก
